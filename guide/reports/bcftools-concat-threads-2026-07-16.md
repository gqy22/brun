# bcftools concat 线程扩展 medium pilot

本报告用于观察普通 `bcftools concat -Oz` 从 1 到 16 线程的扩展趋势，并验证统一 Brun/cgroup
采集链路。实验只有一轮、没有预热且系统负载很高，因此不能作为稳定饱和点结论。

## 输入与环境

| 项目 | 值 |
|---|---|
| 数据集 | `igsr-grch38-wgs-sites` |
| 压缩输入大小 | 977,746,786 bytes |
| 记录数 | 78,229,218 |
| contig 分片 | 23 |
| bcftools / htslib | 1.22.1 / 1.22.2 |
| CPU | Intel Xeon E5-2686 v4 @ 2.30 GHz |
| 物理核 / 逻辑 CPU | 36 / 72 |
| 内存 | 337,953,107,968 bytes |
| 输入与输出存储 | ext4，ST8000DM004-2CX1 机械盘 |
| 开始 load 1m / 5m / 15m | 158.28 / 188.86 / 202.13 |
| 日期 | 2026-07-16 |

输入按 contig 生成 23 个 Header 一致的 VCF.gz 分片。每个方案无预热、正式运行一次，顺序为
1/2/4/8/16 线程和 `--naive`。每轮由独立的 `brun run --require-cgroup` 监控，并同时保留
GNU time 指标；缓存策略为 uncontrolled。

## 原始结果

| 方案 | wall | cgroup CPU | 平均核心 | GNU max RSS | cgroup memory peak | 输出大小 | 相对 1 线程 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 普通 1 线程 | 290.53 s | 227.457 s | 0.783 | 10,644 KiB | 883.3 MiB | 894,463,929 B | 1.000× |
| 普通 2 线程 | 190.23 s | 231.914 s | 1.219 | 11,340 KiB | 885.2 MiB | 894,463,929 B | 1.527× |
| 普通 4 线程 | 139.79 s | 235.935 s | 1.688 | 13,044 KiB | 887.2 MiB | 894,463,929 B | 2.078× |
| 普通 8 线程 | 128.04 s | 240.143 s | 1.876 | 15,216 KiB | 890.9 MiB | 894,463,929 B | 2.269× |
| 普通 16 线程 | 120.42 s | 241.790 s | 2.008 | 22,840 KiB | 898.5 MiB | 894,463,929 B | 2.413× |
| `--naive` | 8.38 s | 2.062 s | 0.246 | 9,456 KiB | 881.2 MiB | 894,186,962 B | 34.669× |

cgroup memory peak 包含该 cgroup 被计费的文件页缓存，不能与进程 RSS 等同。此轮 cgroup
block I/O 均为 0，表示读写被页缓存吸收或尚未形成可归属的块设备 I/O，不表示没有逻辑读写。

## 线程收益

```text
wall reduction(A→B) = (wall(A) - wall(B)) / wall(A) × 100%
average cores       = cgroup CPU seconds / wall seconds
```

| 线程变化 | wall 降幅 |
|---|---:|
| 1 → 2 | 34.523% |
| 2 → 4 | 26.515% |
| 4 → 8 | 8.405% |
| 8 → 16 | 5.951% |

收益在 8 线程附近明显变平。16 线程相对 8 线程仍快 5.95%，刚高于预设的 5% 平台阈值，但平均
CPU 只从 1.876 核增加到 2.008 核，说明 `--threads` 只并行了 concat 路径的一部分。当前更合理的
工作假设是：8 线程接近效率点，16 线程接近本次矩阵的速度点；需要在低负载环境进行至少三轮
平衡实验后才能二选一。

## 正确性

所有方案均对解码后的 78,229,218 条记录计算 SHA-256，结果一致：

```text
7709be05612f1ac39a3083b4e4839e4923675edaf141b59cb5afa2c9fb3f4bcd
```

`--naive` 的压缩字节与普通重压缩输出不同，但本次解码记录一致。它在输入类型和 Header 兼容时
快约 34.67 倍，仍是比增加压缩线程更显著的优化；不能将此结论扩展到不兼容输入，也不能用
`--naive-force` 跳过必要检查。
